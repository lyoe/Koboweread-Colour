# 第 90 版：软件合成 15Hz 单项试验

第 89 版关闭动画的人工反馈为改善不大；三项动画已在新启动期间通过 Android 接口恢复为 `[1,1,1]` 并读回确认。原 JIT 参数、原 APK、原 odex 保留。

本轮只在明确启用时把虚拟 framebuffer 时序从约 30Hz 改为 15Hz：像素时钟从 48225 ps 调为 96450 ps，几何、颜色、双缓冲与翻页接口不变。目的是减少单核 CPU 的软件合成负担，不能预先保证书架加速；也可能增加一帧的调度等待。实际 SurfaceFlinger 查询返回刷新周期 66666666 ns，已确认使用约 15Hz。物理墨水屏仍使用原 REAGL/GC16 策略。

普通菜单默认继续 30Hz。试验由一次显式 `KOBO_WEREAD_DISPLAY_CADENCE=15` 启动，在受控 reading/reuse/interactive 组合下创建根用户私有标记，结束清理时删除。镜像中的原生 framebuffer 库通过该标记选择初始时序。标记在结束前删除不会改变已初始化的进程状态。

真实原生自测分别覆盖默认与 15Hz 的 framebuffer 信息、共享像素、合法翻页、越界与未知 ioctl 拒绝；两档均通过。最初离线测试未挂载 chroot 内的 proc，链接器因此拒绝启动，测试未计为通过；清理后补只读 proc 挂载并完整重跑成功。未据此改变设备 proc 的常规挂载方式。

同一维护阶段修正了清理审计：上一轮结束后两个无引用的实验模块仍加载，已人工卸载。清理函数现在仅对本轮明确加载的三种模块做最多 20 次、间隔 0.1 秒的卸载重试；仍未成功时报告非零，保留已有主故障码。模拟测试覆盖短暂忙碌后释放、已不存在、持续忙碌的次数界限及未知模块拒绝。本轮用户退出后，已实机确认实验进程、挂载、循环设备和三种模块全部清理，KOReader 恢复。

附带可选只读原生 CPU 采样器，最多 180 秒，仅记录固定私有运行环境的进程计时、系统 CPU 计时和可用内存，不读取书库或页面，也不向进程发送信号。它不使用 Binder、不常驻。

人工反馈：第一次返回书架约 14 秒（黑屏约一半），重新开书约 25 秒（黑屏约 10 秒）；再次返回约 5 秒，再次开书约 14 秒。书架仍有“载入中”及部分封面刷新。时间波动较大，未能证实 15Hz 的收益；下一轮恢复默认 30Hz。

约 181 秒采样期间可用内存最低 212848 KiB。完整覆盖的一段约 6.8 秒黑屏中，微信读书主进程平均约 43.6% 单核 CPU，SurfaceFlinger 约 1.8%。另外两段约 9.8 和 8.7 秒黑屏不在 CPU 采样范围内。这些数据支持进一步检查应用内部等待，不能把所有切换等待都归因于 CPU 或排除其他阶段内存压力。原始日志、图像、APK 与预编译缓存不包含在源码包中。
