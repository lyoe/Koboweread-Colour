# 虚拟显示缓冲放入 RAM 的独立对照实验

服务端方法采样发现窗口动画的 `SurfaceControl.nativeCloseTransaction` 两次累计等待约4.9秒和8.5秒，窗口管理和 Activity 暂停通知出现连带等待。它说明需要继续检查合成路径，但尚未确定 SurfaceFlinger 内部的唯一原因。

检查现有实现发现，虚拟 framebuffer 是 ext2 运行镜像内的普通文件，最终位于阅读器存储。软件渲染会弄脏文件映射页并参与写回。此前整机 I/O 数据不能完全归因于此，因此以独立对照验证这条路径的影响。

本实验仅将 `/tmp/kobo-android-runtime/dev/graphics` 挂载为带24MiB容量上限的 tmpfs；实际双缓冲文件为16988160字节，仍由原来的 ioctl 兼容库、SurfaceFlinger 和显示桥使用。它不是把物理 framebuffer 或整个 Android 系统放入 RAM，也不改变分辨率。

原 APK、框架、320 DPI、30Hz、REAGL＋文字增强、堆、动画和 JIT/预编译缓存保持原值。前一轮服务端采样框架不用于本实验，不启动方法采样器。应用数据仍按原方式保存在私有镜像。

## 保护与恢复

- 在原显示服务启动前挂载，拒绝已有挂载及符号链接。
- 只重置每次启动都会重新初始化的临时虚拟 framebuffer，不修改物理设备或应用数据。
- 使用 `nosuid,nodev,noexec`；24MiB是容量上限，不是预先保留全部24MiB。
- 虚拟 framebuffer 的实际 Bionic mmap/pan 探针照常执行，显示和触控仍须真机验证。
- 保留原低内存保护。tmpfs 的页在没有 swap 时不能像普通干净文件缓存一样回收，不能把该方案说成必然更省内存。
- 清理时先停止应用和合成/显示进程，再有界重试卸载 tmpfs；未成功则报告失败，不强制卸载。
- 原生普通菜单和原磁盘版本运行器不替换，作为回退入口。实验入口只由开发控制器调用。

## 比较

使用同一本已下载书，三轮记录开书、返回书架及黑屏时长，轻量记录 CPU、GC、缺页和整机 I/O；不做方法采样。此前人工基线为开书38/17/23秒、返回8/15/22秒。冷热缓存与网络状态仍可能造成波动，单轮变快不足以确认收益。

三轮实际开书与返回已完成，画面精确恢复、tmpfs卸载、KOReader恢复及进程/模块/挂载/loop清理通过，原组件摘要未变。开书中位数23→21秒，返回15→11秒，仍有波动；匹配开书窗口的写入量由几十MiB降至不足1MiB。读取与CPU压力仍明显，不能宣称大幅提速。见[三轮对照结果](三轮对照结果.md)。当前保留为候选，不作为默认版本；完整三十分钟长测尚未完成。
