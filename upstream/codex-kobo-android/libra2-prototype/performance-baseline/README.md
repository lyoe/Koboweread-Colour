# 2.1.2 原生版性能基线

目标是先测量 Libra 2 上真实开书和返回书架的等待，再选择优化点。保留已验证的原 APK、API 24 运行环境、原缓存、1264×1680/320 DPI、30Hz、REAGL＋文字增强；不修改堆、动画或编译参数。

## 采样范围

`counter-sampler.c` 是独立、只读的本机程序，每秒记录：

- 宿主 CPU 累计时间与可用内存。
- 经私有 chroot、执行文件及 UID 核验的 system/main/seg 进程 CPU、缺页、RSS、线程数、I/O 可用性和主线程等待符号；PID 启动时间用于避免混入复用后的进程。当前设备不提供逐进程 I/O，明确记录 `io_available=0`，不能将相应零值当作没有读取；另记录整个 mmcblk0 的存储计数。
- 既有日志中的固定 Activity 开始/显示分类、GC 次数及累计耗时、崩溃/ANR 计数。
- 显示桥已有的帧提交时间、刷新耗时和波形；手势仅记录序号及观察时间。
- 采样器自身 CPU 时间，便于检查诊断开销。

不读取像素缓冲，不保存页面、书名、账号、触控坐标或原始应用日志，不抓线程栈或方法追踪。程序只向标准输出写计数，不向目标进程发信号，也不改变运行配置。

## 时序边界

日志事件按一秒轮询发现，Activity 和手势时间的观察误差约为轮询间隔；不是精确的触摸接收时间。显示桥使用其原始单调时间戳。Activity 显示不等于正文或书架封面全部加载，最终可用时间与黑屏时长仍需要人工计时。GC 总耗时包含并发工作，不能直接等同于主线程暂停时间，也不能与 CPU 用时简单相加。

采样时间使用 CLOCK_MONOTONIC，与显示桥一致；启动器的 `/proc/uptime` 包含休眠时间，两者不能直接混算。程序通过 `CLOCK_PAIR` 同时记录两个时钟以便对齐。采样预检一段约 64 秒的窗口内，采样器 CPU 占单核约 0.75%；这是预检开销，正式交互时仍应核对，不视为零干扰。

进程按五秒周期发现，计数差只在相同 PID 和启动时间内比较；首次样本不代表从采样开始才产生的累计计数。I/O 的 `read_bytes` 为内核记账的实际存储读取，页缓存命中不能仅凭此字段判断。

## 测试顺序

1. 核验 2.1.2 原 APK、框架、原生显示与触控组件，确认旧版实验组件未混入。
2. 启动实际阅读会话，确认原生界面及触控就绪后再开始采样。
3. 人工使用同一本已下载的书，连续三轮“开书→等待正文稳定→返回书架→等待刷新完成”，每一步结束稍停几秒，分别记录总等待和黑屏时间。
4. 下载、网络状态变化、人工全刷等额外操作单独说明，不能混为稳态开书时间。
5. 退出后检查恢复、进程/模块/挂载/loop 清理，保存私有记录并生成不含内容的汇总。

当前为基线测量工具；不代表已经找到瓶颈或证明提速。

`summarize.py counter.log --output summary.json` 可汇总相同进程身份内的 CPU 增量、RSS、缺页、整机 I/O 和刷新时间。汇总不得替代人工记录正文/书架真正可用的时间。

## 构建

使用项目现有 Zig ARM 工具链：

```sh
zig cc -target arm-linux-musleabi -mcpu=cortex_a9 -static -O2 -Wall -Wextra -Werror counter-sampler.c -o counter-sampler
```

设备以 root 在真实交互会话就绪后运行 `counter-sampler 1800`；退出或会话标记失效即停止。最大时限三十分钟，不配置常驻或开机启动。
