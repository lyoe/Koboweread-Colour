# 运行环境资源审计

此工具用于区分应用、Android 合成与辅助服务、显示和输入桥接、KOReader、Nickel、网络、SSH 和其他宿主进程的开销。它只读统计，不修改 APK、运行参数或后台进程。

`resource-audit.c` 在已有轻量采样器上扩展全部进程枚举，每五秒记录 CPU 累计时间、缺页数、RSS、线程数和状态。角色名称为固定白名单；未知进程归入其他类别，不输出命令行、书名、页面、账户、截图或原始应用日志。最多枚举 512 个进程，必须以 root 运行，采样 10～1800 秒，绑定当前阅读会话 ready 文件的设备号与 inode；会话结束或替换时停止。

`summarize.py` 按 PID 和进程启动时间计算增量，避免 PID 复用导致误算。支持 `--start` 和 `--end` 指定单次操作或静止窗口的单调时钟区间。输出采样器自身占用，便于核对测量成本。

限制：RSS 含共享映射，不能相加视为实际物理占用；没有逐线程归因；采样间短命进程可能遗漏；进程 I/O 在目标内核不可用时明确标记不可用。并发 GC 总时间不是界面暂停时间。未知进程和内核线程的分类需要结合私下设备审计核对。内存独占情况另用选定进程的 smaps 数值汇总验证，避免周期性扫描 smaps 干扰计时。

本次先沿用已完成短期测试的 RAM 显示缓冲实验入口，保持原 APK、框架、原生分辨率、30Hz、REAGL、堆和编译缓存。常用 KOReader 入口不变。开始采样不代表完成优化或稳定性验证。

## 有容量限制的热点页面试验

`hot-pages.c snapshot PID` 读取目标主进程的只读代码映射和 pagemap 驻留位，只接受当前 chroot、原应用 UID 和固定主进程身份。仅选取驻留且仍为文件页的映射，排除匿名写时复制页面。输出 APK、ODEX、允许的动态库、启动镜像与字体文件的 inode、大小及驻留页偏移，不读取代码或资源内容，也不扫描书籍数据库、账户或用户文档。空快照、进程替换和会话更换均判失败。

`build-hot-plan.py BEFORE AFTER PLAN` 合并重复映射，选择两次快照之间新增驻留的代码页，最多 24 MiB，不会为了用满预算补入无依据的页面。优先选择 ODEX，再选动态库、APK、启动镜像与字体。PTE 驻留说明页面曾被使用，不能证明该文件造成的缺页成本或未来复用价值，必须通过对照试验验证。

`hot-pages.c keep PLAN` 验证会话及文件身份后，对原文件的选定范围建立只读共享映射并 mlock，保留原有页缓存，不复制 APK、不改应用堆或持久数据。计划必须由 root 持有且模式 0600，拒绝符号链接和白名单外路径。所选页总量不超过 24 MiB，若 MemAvailable 低于 128 MiB 则释放；会话完成标记、ready 文件变化、信号或十分钟期限也会触发释放。输出预热耗时、实际保留量与释放状态。

这些页面原本可能已在缓存中；mlock 会降低其可回收性，不能将其视为零内存成本。预热耗时须计入收益评估；工作集、后台同步、温缓存和测试顺序均会影响结果。此工具不保证加速，也不替代日常入口，正向设备试验与退出清理必须单独验证。

设备上的计划应存放于实验镜像内的 ext2 私有目录。机内 `/mnt/onboard` 的 FAT 文件系统不能可靠提供逐文件 0600 权限，工具会拒绝这种计划，不应放宽权限检查。

本轮实际结果见[热点缓存试验结果](热点缓存试验结果.md)：锁定约 18.5 MiB 的方案未显示加速，已释放，不用于日常入口。

## 线程 CPU 与有限优先级试验

`thread-cpu.c` 每两秒读取原应用、阅读子进程、系统服务和 SurfaceFlinger 的线程 CPU 累计值。输出固定类别，不输出原始线程名、页面或栈。使用进程与线程启动时间区分 PID/TID 复用，最多观察九百秒，会话结束或收到停止信号时退出。`summarize-threads.py LOG [--start T --end T]` 分开汇总进程 CPU 与线程 CPU，不将二者相加，并报告采样覆盖率和采样器自身成本。短命线程和采样边界会造成遗漏。

`thread-priority.c observe|boost SECONDS` 为开发对照工具，需独立、单实例启动。只接受当前 chroot 中 UID 10007 的微信读书主进程及阅读子进程；仅选择固定通用和网络工作线程名称前缀，且当前 nice 不小于 10 的线程，将其调整到 5。主线程、JIT、GC、系统服务和原本优先级更高的工作线程不变。

工具最多运行五分钟，记录每次实际调整前的值，正常退出、可处理信号或会话结束时逐线程核对 PID、TID 和启动时间并恢复。若应用自行改变优先级则不覆盖它的新值，进程或线程已退出则跳过。此工具不是日常调度策略，不能通过强杀来验证恢复。

本轮设备检查确认 8 个线程实际调整、随后全部恢复，未显示开书加速。完整结果见[线程 CPU 与优先级试验结果](线程CPU与优先级试验结果.md)。日常入口保持原配置。
